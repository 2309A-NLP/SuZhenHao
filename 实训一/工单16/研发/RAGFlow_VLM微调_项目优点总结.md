# RAGFlow VLM 微调项目 — 项目优点总结

> **项目**：工单16 — 基于 Qwen2-VL-2B-Instruct 的专利图纸问答 VLM 微调  
> **技术栈**：RAGFlow + LLaMA-Factory + QLoRA + DeepSpeed  
> **硬件环境**：RTX 4060 (8GB 显存) + WSL2 Ubuntu  
> **总结时间**：2026年6月23日

---

## 一、精准的问题定义 — 从 RAG 到 VLM 的技术跃迁

### 1.1 识别问题本质

本项目最核心的优势在于**精准识别了纯文本 RAG 系统的根本局限**。工单15 将 RAG 系统的准确率从 0% 优化到 100%，但那是在答案可从文本中检索到的前提下。工单16 面对的问题本质不同：

> **当答案就在专利图纸上，纯文本系统永远"看不见"它。**

项目没有继续在 RAG 框架内修补（调整分块策略、优化检索、改进 Prompt），而是做出了正确的技术判断：**将系统从纯文本模态扩展到视觉-语言多模态**。这种从"检索优化"到"模态扩展"的跃迁，体现了对问题本质的深刻理解。

### 1.2 三类问题的科学分类

项目将 10,096 道题目精准划分为三个类别，每个类别对应明确的技术需求：

| Group | 类型 | 典型问题 | 技术需求 |
|-------|------|---------|---------|
| **Group 1** | 文本理解 | "哪个部件不包含在自动水平除尘机中？" | 纯文本推理 |
| **Group 2** | 图纸位置 | "编号8的部件相对于编号7的位置是什么？" | 视觉空间理解 |
| **Group 3** | 图纸推理 | "调整支撑板距离，会直接影响哪个部件？" | 视觉+逻辑推理 |

**优势体现**：分类不是笼统的"让模型看图"，而是精确区分了哪些题需要看图、看什么图、怎么看。这使得后续的数据集构建、训练策略和效果评估都有了明确的针对性。

## 二、智能数据工程 — 按需提取的精简策略

### 2.1 按页码引用的精准图片提取

项目没有简单地将每份 PDF 的所有页面都转成图片（那样会产生数十万张无用图片），而是：

1. 用正则表达式 `第(\d+)页` 扫描每道题目，提取引用的具体页码
2. Group 1 纯文本题只提取第 1 页（封面）作为占位图
3. Group 2/3 只提取题目所引用的特定页码

**实际效果**：1,700 份 PDF、10,096 道题 → 仅提取约 3,400 张图片，而非数十万张。数据量减少 95% 以上，同时保证每张图片都对应至少一道实际题目，信息密度极高。

### 2.2 ShareGPT 格式的精心设计

每条微调样本的格式经过深思熟虑：

```
用户输入: <image>问题内容 + 选项
助手输出: 答案字母 + 完整选项文本
```

**设计要点**：
- `<image>` 标记明确告知模型需要查看图片
- 助手回复同时包含**答案字母**和**完整选项文本**，帮助模型学习标准答题格式
- 使用绝对路径，兼容 WSL 环境
- 8:1:1 的 train/val/test 划分比例经典且合理

### 2.3 多进程并行提取

图片提取使用 `ProcessPoolExecutor(max_workers=4)` 实现 4 进程并行处理，充分利用多核 CPU，大幅缩短了 1,700 份 PDF 的处理时间。

## 三、极限显存下的 QLoRA 工程

### 3.1 硬件约束下的最优技术选型

在 RTX 4060 的 8GB 显存上微调 2B 参数的视觉语言模型，这是一个极具挑战的场景。项目通过多项技术的巧妙组合，将不可能变为可能：

| 技术 | 作用 | 显存节省效果 |
|------|------|------------|
| **4-bit NF4 量化** | 基座模型权重从 FP16 压缩到 4-bit | ~4GB → ~1.5GB |
| **LoRA (rank=16)** | 仅训练 ~3000 万参数（1.5%） | 可训练参数显存极小 |
| **梯度检查点** | 前向传播不保存中间激活值 | 用计算时间换显存空间 |
| **gradient_accumulation=8** | 等效 batch=8，实际仅需 batch=1 的显存 | 前向传播仅需 1 份显存 |
| **DeepSpeed ZeRO-2 + CPU Offload** | 优化器状态分片到 CPU | 进一步减少 GPU 占用 |

**组合效果**：在 8GB 显存内成功运行 2B 参数 VLM 的微调，显存占用控制在 3-4GB。

### 3.2 LoRA 配置的合理性

每个参数的选择都有明确的技术理由：

| 参数 | 选择 | 理由 |
|------|------|------|
| rank=16 | 适中 | rank=8 表达力不足，rank=32 显存压力大 |
| alpha=32 | rank 的 2 倍 | 标准做法，缩放因子 = alpha/rank = 2 |
| target=all | 所有线性层 | 覆盖 attention、MLP、gate，最大化微调效果 |
| dropout=0.05 | 轻度正则化 | 防止在小数据集上过拟合 |

## 四、迭代优化的工程方法论

### 4.1 三个版本的配置迭代

项目经历了三个配置版本的迭代演进，每次都基于实际训练中遇到的真实问题：

| 版本 | 关键变化 | 迭代原因 |
|------|---------|---------|
| **v1** | cutoff_len=512, epochs=3, max_samples=10000 | 初始配置 |
| **v2** | cutoff_len=**600**, epochs=**1**, max_samples=**2000** | 图片 token ~280 + 文本，512 不够；3 epoch 过拟合 |
| **v3** | max_steps=**250**, peft/quant 分离写法 | 用 step 精确控制训练量；配置格式更稳定 |

### 4.2 问题驱动的诊断过程

**v1 → v2 的问题诊断**：
- cutoff_len=512 时，图片占用约 280 个 token，仅剩约 230 个 token 给问题和选项文本，部分长题目被截断 → 提升到 600
- 3 个 epoch 在 10,000 样本上训练过多，模型出现过拟合 → 降到 1 个 epoch
- eval 策略在某些超长序列的 batch 上卡住 → 关闭中途评估

**v2 → v3 的问题诊断**：
- v2 的简化 YAML 格式可能缺少某些隐藏配置项，导致训练静默退出 → 改用 v1 的 peft_config/quant_config 分离写法
- epoch 控制不够精确 → 改用 max_steps=250 精确控制训练量

**核心优势**：不是一次性写好配置就跑，而是**训练→诊断→调整**的迭代循环。这种工程方法论确保了最终配置是经过实际验证的。

## 五、严谨的评估设计

### 5.1 贪心解码的评估推理

评估脚本的推理参数经过精心设计，确保结果完全可复现：

| 参数 | 值 | 目的 |
|------|-----|------|
| do_sample=False | 贪心解码 | 结果完全确定性 |
| temperature=0.01 | 接近 0 | 即使采样也几乎确定性 |
| top_k=1 | 只保留最优 | 最严格的解码策略 |
| top_p=0.001 | 极小核采样 | 几乎排除随机性 |

**优势**：评估结果的差异完全来自模型能力的差异，不受采样随机性干扰。

### 5.2 鲁棒的答案提取

答案提取策略覆盖了多种模型输出格式：
- 开头单字母：`A`
- 带句号：`A.`
- 带顿号格式：`A、`
- 匹配不到则视为预测错误

**优势**：考虑了模型输出格式的多样性，避免因格式不一致导致的假性错误或假性正确。

### 5.3 科学的抽样策略

从 1,011 条测试集中随机抽样 300 条进行评估，兼顾三个维度：
- **统计显著性**：300 条样本足够反映整体表现
- **评估效率**：全量评估耗时过长（每条需要数秒推理）
- **可复现性**：固定 RANDOM_SEED=42，保证每次抽样结果一致

## 六、显著的微调效果

### 6.1 基座 vs 微调对比

根据实际评估数据：

| 指标 | 基座模型 | 微调模型 | 提升 |
|------|---------|---------|------|
| **总准确率** | 29.7% | 67.7% | **+38.0%** |
| 正确数 | 89/300 | 203/300 | +114 |

**38 个百分点的绝对提升**，这是一个非常显著的改进。微调后的模型准确率是基座模型的 2.3 倍。

### 6.2 基座模型的表现分析

基座模型的 29.7% 准确率并非来自真正的工业图纸理解能力。从错误分析可以看到：
- 基座模型的回答格式不稳定（有的输出完整句子，有的输出选项字母）
- 很多回答是基于预训练中的通用视觉理解，而非针对专利图纸
- 微调后格式统一为 `字母 + 完整选项`，实际可用性大幅提升

### 6.3 微调模型的错误模式

微调模型的错误主要集中在以下几类，为后续优化提供了明确方向：
- **空间方向混淆**：上下/左右判断错误（视觉理解中最难的部分）
- **复杂推理链**：需要多步推理的题目（如"A 直接驱动 B，B 再影响 C"）
- **流程图理解**：步骤顺序和流程判断错误

## 七、完整的端到端流水线

### 7.1 四阶段自动化

项目构建了从原始数据到效果评估的完整流水线：

```
Stage 1: extract_images.py
  10,096 条问题 + 1,700 份 PDF → ~3,400 张页面图片
  按需提取，DPI=200，4 进程并行

Stage 2: build_dataset.py
  问题 + 图片 → ShareGPT 格式 JSONL
  8:1:1 划分 → train(8,076) + val(1,009) + test(1,011)

Stage 3: LLaMA-Factory QLoRA
  Qwen2-VL-2B + NF4 + LoRA(r=16, α=32)
  250 steps, batch=8(有效), lr=1e-4

Stage 4: evaluate.py
  抽样 300 条，基座 vs 微调对比
  输出 evaluation_report.json + error_analysis.json
```

### 7.2 模块化设计

每个脚本都可以独立运行，不依赖其他阶段的输出（前提是上游数据已准备好）：
- `extract_images.py` → 只需 questions.jsonl 和 PDF 文件
- `build_dataset.py` → 只需 questions.jsonl 和图片目录
- `evaluate.py` → 只需测试集和模型权重

**优势**：模块化设计使得每个阶段可以独立调试、重跑、验证，不会因为一个阶段的失败导致整个流程崩溃。

### 7.3 一键部署脚本

`deploy_vlm_finetune.sh` 提供了完整的一键部署能力：
- 支持 `--check`、`--extract`、`--dataset`、`--train`、`--evaluate` 分步执行
- 自动检查系统环境、GPU、依赖、模型文件
- 自动生成 DeepSpeed 配置文件
- 彩色日志输出，操作友好

## 八、硬件感知的工程优化

### 8.1 显存感知设计

项目的每个配置参数都充分考虑了 8GB 显存的硬约束：

| 配置 | 显存影响 | 设计考量 |
|------|---------|---------|
| cutoff_len=600 | 输入序列显存 | 图片 token ~280 + 文本 ~320，刚好够用 |
| batch_size=1 | 前向传播显存 | 最小 batch，用 grad_acc=8 补偿 |
| NF4 量化 | 模型权重显存 | 4-bit 压缩，基座仅占 ~1.5GB |
| gradient_checkpointing | 中间激活值显存 | 用计算时间换显存空间 |
| DeepSpeed ZeRO-2+Offload | 优化器状态显存 | CPU 内存分担 GPU 压力 |

### 8.2 故障恢复机制

- **图片提取**：已存在的图片自动跳过（`if os.path.exists`），支持断点续传
- **数据集构建**：检查已有数据集，避免重复构建
- **训练**：`save_total_limit=2/3` 控制 checkpoint 数量，防止磁盘占满
- **评估**：单条出错时 try-catch 跳过，不影响整体评估进度

### 8.3 多种 DeepSpeed 配置

项目提供了 4 种 DeepSpeed ZeRO 配置，适应不同硬件环境：

| 配置 | ZeRO Stage | CPU Offload | 适用场景 |
|------|-----------|-------------|---------|
| ds_z2_config.json | Stage 2 | 无 | 显存充裕时，速度最快 |
| ds_z2_offload_config.json | Stage 2 | 优化器 | **RTX 4060 8GB 推荐** |
| ds_z3_config.json | Stage 3 | 无 | 多卡训练 |
| ds_z3_offload_config.json | Stage 3 | 全部 | 极端显存受限 |

## 九、技术选型的系统性优势

| 决策点 | 选择 | 原因 |
|--------|------|------|
| 基座模型 | Qwen2-VL-2B-Instruct | 2B 参数适合 8GB 显存；中文和图表理解能力强 |
| 微调方法 | QLoRA (4-bit NF4) | 8GB 显存唯一可行方案 |
| 训练框架 | LLaMA-Factory | WebUI + CLI 双模式，对 Qwen2-VL 原生支持 |
| 图片提取 | PyMuPDF (fitz) | 轻量级 PDF 处理，按页渲染，无需 OCR |
| 量化工具 | bitsandbytes | HuggingFace 生态标准方案 |
| 评估策略 | 贪心解码 + 字母匹配 | 确定性结果，简单可靠 |
| 数据格式 | ShareGPT JSONL | LLaMA-Factory 标准格式，兼容性好 |

## 十、项目整体优势总结

本项目的核心优势体现在以下几个层面：

1. **技术判断力**：从 RAG 到 VLM 的模态扩展决策，体现了对问题本质的深刻理解
2. **数据工程**：按需提取策略将数据量精简 95%+，信息密度极高
3. **硬件适配**：在 8GB 显存极限下，通过 QLoRA + DeepSpeed 成功微调 2B 参数 VLM
4. **工程方法论**：三版配置迭代，每次基于实际问题诊断，而非凭感觉调整
5. **评估严谨性**：贪心解码保证可复现，多格式答案提取保证鲁棒性
6. **效果显著**：准确率从 29.7% 提升到 67.7%，绝对提升 38 个百分点
7. **端到端自动化**：完整四阶段流水线，一键部署，模块独立可运行

> **一句话总结**：在 8GB 显存的硬约束下，用 QLoRA 成功微调 2B 参数视觉语言模型，使专利图纸问答准确率提升 38 个百分点，同时构建了完整的端到端自动化流水线。
